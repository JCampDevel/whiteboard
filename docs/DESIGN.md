# Design

The requirements are in [REQUIREMENTS.md](REQUIREMENTS.md); R1 to R17 below refer to them.

## Parts

- `whiteboard/model.py`: the diagram data and all validation. R4 is enforced here (an edge's source and target must be two different, existing nodes), so the server rejects a bad diagram even if the page has a bug.
- `whiteboard/server.py`: `http.server` on 127.0.0.1 only. `GET /api/diagram`, `PUT /api/diagram` (validated, written atomically), and three fixed static files. Nothing else is served, so there is no path to traverse.
- `whiteboard/static/`: single-page SVG editor. Holds the diagram in memory and redraws on every change; it is written to the project file only when the user saves.

## Decisions

- **Browser, not Tkinter (R17):** `tkinter` is not installed for the system Python, and installing it needs sudo. The browser version needs nothing.
- **Arrow ends (R4, R5):** an arrow stores the ids of its two boxes plus `source_anchor` and `target_anchor`. An anchor is either `null`, meaning the end **floats** (follows its box), or a fixed point on the box's outline as fractions `[x, y]` of its width and height (so it stays put when the box is moved or resized). This is the draw.io / Visio model. Floating ends are worked out on every redraw (`computeFloating`): each takes the side of its box facing the other box (overlapping boxes, such as an inner box and its own Controller, go by their centres), or, if the short straight stub out of that side would run into another box, the next best side (the two sides across, then the far side). Ends sharing a side are spread evenly along it, ordered by where their other box lies so that they don't cross; so a Control Action and a Feedback between the same two boxes get separate lanes on their own. Fixed points come from where an end is dropped: within 12 px of one of the box's twelve **connection points** (a quarter, half and three quarters along each side) it snaps to that point; within 8 px of the outline it fixes there; anywhere else on the box it floats. Files from before 0.10 have fixed anchors on every arrow; they keep them until reset.
- **Panning, not scrolling (R10):** the page keeps a view offset and draws everything in a translated group, so the canvas is unbounded in every direction (negative coordinates are fine) and there are no scrollbars. Pan = Pan tool, Space+drag, middle button or wheel.
- **Selection (R11):** a set of ids (rectangles and arrows). Dragging empty space with the Select tool draws a box that selects rectangles it touches and arrows whose both ends are inside it. Dragging any selected rectangle moves all selected rectangles; arrows follow because they only store anchors. A plain click inside a group that doesn't move narrows the selection to that item. The resize handle shows only when exactly one rectangle is selected; arrow-end handles show on every selected arrow.
- **Arrow routing (R18):** `static/route.js`, pure functions with no page access. An arrow leaves and enters its boxes at right angles (the side the attachment point is nearest to) with a short straight stub, then the cheapest right-angled path between the stub ends is found with A* over a grid whose lines run along the padded edges of nearby boxes and through the two ends (plus the midpoints, so a simple Z-bend is centred). Cost is length plus a penalty per corner, so it prefers few bends; U-turns are not allowed. Obstacles are all boxes except those the arrow is connected to, the Controller around a connected inner box, and the inner boxes of a connected Controller (the page works that out in `obstaclesFor`). Boxes are padded by 10 px, so an arrow keeps clear of them; only boxes within 300 px of the two ends are considered. If the ends are boxed in or the boxes are too close for the stubs, it falls back to a plain two-bend right-angled link that may cross a box. Routes are recomputed on every redraw and are not remembered, and two arrows heading the same way can share a corridor (they are not spread apart). The arrow's label sits half way along the route.

  *Moving segments (R18):* a selected arrow shows a square handle in the middle of each inner straight segment (not the two at its ends, which are tied to the boxes). Dragging one slides that segment sideways only (a horizontal one up and down). It is stored as a pinned point in `via`, `[x, y, axis]`, and the router must pass straight through it along that axis (it may only arrive there horizontally for axis 0, vertically for axis 1), so the segment stays where it was put while the router still goes round boxes before and after it. A moved segment's handle is filled; double-clicking it removes the pinned point. Points pinned by 0.7 to 0.9 corner dragging (`[x, y]`, no axis) still work and show as moved segments. **Reset arrow** clears both fixed ends and every pinned point of the selected arrows. Small movements (under 3 px) of a handle are ignored, so clicking or double-clicking never pins anything.
- **Connection feedback (R5):** with the Select or an arrow tool and no button held, the box under the mouse shows its connection points (in the overlay layer, not saved), and the one you would snap to is filled. In Select, pressing within 7 px of a connection point starts a new arrow from it (the kind of arrow last picked in the toolbar, Control Action at first); pressing anywhere else on the box still selects and moves it, so moving boxes is not affected. While drawing an arrow or dragging an arrow end, the box under the pointer is ringed, shows its points, and a dot marks where the end would land. A drag released over empty space or the arrow's other box does not change the connection. Double-clicking an end handle sets that end floating again.
- **Names (R7):** the `label` field. It is edited only in the tables: the Name cell of each row is a text box, and the diagram updates as you type. (There is deliberately no name field in the toolbar.) Names are free text, up to 200 characters, and needn't be unique; the unique ID is what identifies an entity. Whether a name is drawn is the `name` entry of the entity's `shown` list, switched by the tick box in the same cell (see Properties of an entity). Typing saves after a short pause and the table then redraws; the page puts the cursor back where it was in the box so typing isn't interrupted. In the table a name is plain text (or "(no name)" in grey) until it is double-clicked, so a stray click can't change it; then it becomes a text box. Enter keeps the name, Esc puts the old one back, and leaving the box ends editing. Which cell is open is remembered across the table's redraws (`editingName`), and a flag stops the redraw's own removal of the box being mistaken for the user finishing. Double-clicking an item on the diagram opens the tables (if minimised) on that item's row with its name open for typing, which is the quick way to rename from the diagram. Clicking the diagram releases the box so Delete and the tool keys work again.
- **Unique IDs (R6):** an ID is the type's prefix plus a number (C Controller, CA Control Algorithm, PM Process Model, CP Controlled Process, A Control Action, F Feedback). The model rejects an ID whose prefix doesn't match the item's type, and duplicates across all items, so an ID identifies exactly one entity and says what it is. The page picks the next number as highest-in-use plus one; a number is reused only if the highest one was deleted.
- **Inner boxes (R2):** a Control Algorithm / Process Model is an ordinary node with a `parent` (a Controller); the model allows at most one of each per Controller and nothing else may have a parent. Their position and size are *derived* from the Controller by the page on every draw (so they follow it), but are still saved with the other geometry. They can't be moved, resized or deleted separately. Arrow anchors work on them exactly as on other boxes.
- **Tables panel (R13, R14):** a dock under the diagram (the diagram area shrinks to fit; the Tables bar is always visible). One tab per entity type, one table shown at a time. Selecting items on the diagram while the dock is open switches to the table of the item selected last and highlights the rows of all selected items in it (`tr[data-id]`, unique because IDs are unique); the dock refetches after each successful save and re-applies the highlight. A minimised dock does nothing on selection and catches up when opened.
- **Table layout (R13):** each cell is a small flex row (tick box, then value), which is what keeps a tick to the left of a name. Tables use fixed column widths from a `<colgroup>`; each heading has a grip on its right edge to drag. Minimum width is ten characters of the page font (measured, `10ch`) plus room for the tick box and padding, so at least ten characters of text are visible beside the tick. Widths are remembered per table and column in the browser's local storage. Arrow tables get one extra column, **On diagram**, which is not a property of the model: it is the arrow's `hidden` flag, inverted.
- **Description and effect (R20):** two free-text fields on arrows, `description` (Control Actions only) and `effect` (Feedback only), up to 1000 characters each (names stay at 200). The model refuses a non-empty description on a Feedback or effect on a Control Action. Each is one more property in `FIELDS`: a column in its table (after Name), a tick box to show it on the diagram, and a text cell edited the same way as a name (double-click, Enter keeps, Esc restores). "The entity being pointed at" is simply the arrow's **To** column; the effect is not a link to anything, it is the author's words. On the diagram the live text is used (not the table's, which can lag), cut to 70 characters so a long note doesn't run across the canvas; the table shows it in full.
- **Relationships (R21):** a third list in the diagram, `relationships`, beside `nodes` and `edges`: each is `{id, arrows, description}`, with ids R1, R2, ... (unique across everything, like all ids). The model requires at least two arrows, each listed once and each an existing arrow (not a box). Older files have no list and open with none; the file format version is unchanged, since an optional list was added. **Add relationship** in the toolbar works when two or more visible arrows are selected (boxes in the selection are ignored); it opens a dialog listing the arrows, with a box for the description, and adds the relationship to the end of the list and shows the Relationships table. That table (built by `model.tables` like the others) has ID, Arrows and Description columns and a Remove button; the description is edited by double-clicking, as names are. Relationships aren't drawn, so the table has no tick boxes. Clicking a relationship's ID selects its arrows and centres the view on them, keeping the Relationships table in front. Each arrow table has a **Relationships** column listing the relationships the arrow is in; it is an ordinary arrow property, so it can be ticked to show on the arrow. Deleting arrows removes them from relationships, and a relationship left with fewer than two arrows is deleted; hiding an arrow leaves its relationships alone.
- **Hiding arrows (R19):** `hidden` is saved on the arrow. A hidden arrow is not drawn, cannot be selected on the diagram (select-all and box-select skip it, so Delete can never remove something you can't see), and still has its table row and links. It is hidden and shown with the **On diagram** tick in the arrow tables (the heading tick does all rows), with **Hide arrow** in the toolbar for the selected arrows, and **Unhide arrows (n)**, shown only while some are hidden, brings them all back. Deleting a box deletes its arrows, hidden or not.
- **Tables (R12):** built in Python (`model.tables`, served at `POST /api/tables`) rather than in the page, so the linking rules are unit tested. The page sends the diagram on screen, saved or not, a quarter of a second after each edit, and only uses the answer to its latest request. Direction rules: a Controller / Control Algorithm / Process Model lists *outgoing Control Actions* and *incoming Feedback*; a Controlled Process lists *incoming Control Actions* and *outgoing Feedback*. Arrows of any other kind or direction land in "Other arrows", which exists only so that no arrow drawn the unusual way round is silently missing from every table; it can simply be left unticked. For a Controller, the arrows of its two inner boxes count as its own, and arrows between its own inner boxes are listed as "(internal)".
- **Properties of an entity (R12, R15):** `model.FIELDS` lists, for each type, its properties in table-column order. It is the single source for the table's columns *and* for which properties may be switched on to show on the diagram, so the two cannot drift apart. Each entity saves `shown`, the list of its property keys ticked (default `["id", "name"]`; the model rejects a key its type doesn't have, and tidies the list into column order). Each table cell has a tick box for its entity and property; a header tick box sets the whole column. On the diagram, ID is drawn as the small caption (arrows: before the name), name as the main text, and any other ticked property as an extra line of smaller muted text, `Title: value` (value `—` if empty). Box text is clipped to the box (a Controller's to its left half), so enlarge a box to see long lists. The *values* of linked properties come from the same server tables (so they are the tested ones); the page refetches them after every save, so these lines can lag an edit by a moment. ID and name are always taken live from the diagram.
- **Colours (R8):** a colour chart (16 swatches: 15 hues plus Default) opens from the toolbar and applies to the selected items, or, with nothing selected and a drawing tool active, to the next item of that type; each type remembers the colour last given to it. A colour is stored as `#rrggbb`, or `auto`, which draws in the theme's text colour. `auto` is the default for arrows (and the swatch labelled Default), because a fixed dark default would vanish on the dark theme. Existing arrows with the old near-black default (`#111827`) become `auto` when a file is opened. The model still accepts any hex colour, so files with colours outside the chart keep them.
- **Theme (R9):** colours are CSS variables. The default follows the system (`prefers-color-scheme`); the toolbar button cycles Auto, Light, Dark and saves a forced choice in the browser's local storage, applied by a small script in `<head>` before first paint to avoid a flash. Nothing in the drawing is hard-coded to one theme: shapes use their own colour or the text colour variable.
- **Old files (R16):** `model.migrate` upgrades older files when they are read (current ID prefixes, inner boxes added, old default arrow colour becomes `auto`). It is idempotent and doesn't change the input.
- **File format (R16):** indented JSON (2 spaces), one field per line, so it can be read, compared and edited in a text editor. It starts with `"format": "whiteboard-diagram"` and `"format_version": 1`, then `nodes` and `edges`. Node: id, type, x, y, w, h, label, colour, parent (inner boxes only), shown. Edge: id, type, source, target, style, label, colour, source_anchor, target_anchor, shown, via, hidden, description, effect. Then `relationships`: id, arrows, description. `colour` is `#rrggbb` or `auto`; an anchor is `null` (end follows its box) or `[x, y]`. A file with a different `format` is refused with a clear message, and so is a `format_version` above the one this app knows; a file with no `format` at all (from before 0.11) is accepted. `format_version` only goes up if a change means older versions of the app could not read the file; added optional fields don't count.
- **Projects (R16):** the server holds the open project's file, or none. Started without `--file` it has none and the page shows the **start screen** (a full-window panel over the app); with `--file` that project is open from the start. The start screen's **New project…** and **Open project…**, and the toolbar's **Save copy…**, share the page's own file dialog (folders and `.json` files via `GET /api/browse`, Up and Home folder), because only some browsers let a page show a real save dialog and none tell a page where an opened file lives. The dialog starts in the open project's folder, otherwise the last folder used, otherwise Documents (or home).
  - *New* (`POST /api/new` with folder and name): the name becomes the file name (`.json` added); an existing file is replaced only after "Replace it with a new, empty project?" (409 until the page sends `overwrite`). The empty diagram is written straight away, so the project exists on disk from the start, and becomes the open project.
  - *Open* (`POST /api/open`): loads, upgrades if old and validates the file, and only then makes it the open project, so a bad file changes nothing and the dialog shows why.
  - *Save* (`PUT /api/diagram`, button and Ctrl+S) is the only thing that writes the project. Edits mark the project unsaved (a dot after its name in the toolbar and tab, the Save button lit, status "Unsaved changes"); `beforeunload` makes the browser ask before the tab is closed or reloaded with unsaved changes. A save that finishes after a newer edit doesn't mark that edit saved.
  - *Save copy* (`POST /api/save-copy`, Ctrl+Shift+S) writes the diagram on screen, saved or not, to another file, asking before replacing one, and refuses the project's own file. The open project doesn't change, so later saves never touch the copy.
  - *Close project* asks "Save changes to X before closing?" with Save / Don't save / Cancel when there are unsaved changes (Cancel stays; if saving fails it stays and the status says why), then `POST /api/close` and back to the start screen, with everything from the project cleared from the page. Closing itself writes nothing.
  - With no project open, the server refuses to load or save (409), and keyboard shortcuts are off.
  - Questions use the page's own `<dialog>` (`choose()`), with up to three buttons, because the browser's `confirm()` can only say OK and Cancel.
- **Never overwrite a file that couldn't be read:** if the project file can't be loaded (damaged, not a diagram, from a newer version), the server remembers why and refuses to save over it (409, with the reason and "use Save copy…"). When the app is started with such a file the page goes to the start screen and shows why. Each save also says which project file the page thinks it is saving (`X-Whiteboard-File`); if the open project has changed since, the server refuses it. Saving through a symbolic link writes the file it points to and keeps the link.
- **Server safety:** the server listens on 127.0.0.1 only. Since it can now list folders and write files, it also refuses any request whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` (which defeats DNS rebinding, where another site points its own name at your machine), and any `/api/` request without the `X-Whiteboard: 1` header. A page from another site can't add that header without the browser first asking this server, which never says yes; so other web pages open in the same browser can't read your folders or write files through it. The page adds the header on every request (`api()`).
- **Toolbar stays put:** the status and file name sit in an area that takes the room left over and shrinks (cutting text with "…", full text on hover), instead of a box that grows with its message. The Theme button has a fixed width, and **Unhide arrows (n)** is always present (greyed out at 0) instead of appearing and disappearing, so nothing changes the toolbar's length.
